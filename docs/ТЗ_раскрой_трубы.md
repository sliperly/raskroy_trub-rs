# ТЗ на программу раскроя трубы (Rust-версия; в виде промпта для разработки)

## Контекст и цель

Нужна консольная программа на **Rust**, которая читает Excel-файл
производственного графика, формирует раскрой заготовок труб на хлысты
6000 мм и сохраняет результат в виде текстовых файлов, сгруппированных по
материалу. Это переписанная на Rust версия существующей Python-программы
(репозиторий-оригинал: см. README); поведение, форматы файлов и тексты
сообщений должны остаться **идентичными** оригиналу, меняется только
реализация.

Готовый результат — один самодостаточный `.exe` (`cargo build --release`),
который запускается на компьютере без Rust и без Python, без установки
каких-либо зависимостей. Код должен работать из любой рабочей папки, не
требовать ручной настройки путей и быть терпимым к вариациям структуры
исходного Excel-файла.

## Технологический стек и требования к реализации (Rust)

- Rust, edition 2024, стабильная ветка компилятора; без `unsafe`.
- Чтение `.xlsx` — крейт `calamine` (только чтение, Excel устанавливать не
  нужно). Регулярные выражения — крейт `regex` (учесть, что в нём нет
  lookahead/lookbehind: маскирование "диаметр"/"отв" делать заменой
  найденных фрагментов, а не просмотром вперёд/назад).
- Генератор случайных чисел для мультистарта — лёгкий крейт (`fastrand`) или
  собственный xorshift; тяжёлые зависимости не нужны.
- Остальное — стандартная библиотека: `std::fs`, `std::path`,
  `std::time::Instant` (бюджет времени), `std::collections::HashMap`.
- **Никаких паник на пользовательских данных.** Все ошибки окружения и
  данных возвращаются как `Result<_, ОшибкаПрограммы>` и печатаются
  понятным русским сообщением; `unwrap()`/`expect()` допустимы только там,
  где ошибка невозможна по построению. Паника с трассировкой для
  пользователя недопустима.
- Бинарник должен собираться без внешних системных библиотек (для
  Windows — таргет `x86_64-pc-windows-msvc` или `-gnu`). Для уменьшения
  размера в `Cargo.toml` профиль `release`: `lto = true`, `strip = true`,
  `codegen-units = 1`.
- Кодировка всех выходных файлов — UTF-8. Имена файлов и папок — с
  кириллицей, учитывать ограничения Windows (см. раздел "Структура
  результата на диске"). Консоль Windows может показывать русский текст
  некорректно в старых окнах `cmd`: при старте включить UTF-8-вывод
  (кодовая страница 65001), если это возможно без внешних зависимостей.
- Структура проекта (рекомендуемая, не жёсткая): `src/main.rs` (точка входа,
  пауза перед закрытием), `src/excel.rs` (чтение и поиск раздела),
  `src/parse.rs` (длина, материал), `src/pack.rs` (упаковка),
  `src/geometry.rs` (iges), `src/report.rs` (вывод файлов), `tests/`
  (интеграционные тесты на синтетических `.xlsx`).

## Физическая модель раскроя

- Исходная труба: **6000 мм**.
- Первым делом отрезается **калибровочный кусок 30 мм** — это происходит
  ДО начала резки деталей, кусок сразу отпадает. Поэтому в итоговую обрезь,
  которую в конце видит оператор, он **не входит** (это отдельный, всегда
  ровно 30-мм кусок, а не часть "хвостового" остатка).
- Суммарные технологические потери для расчёта рабочей зоны: **255 мм**
  (30 мм калибровка + 215 мм зажим станка + 10 мм запас на ручную
  установку — величина увеличена сознательно: лучше несколько лишних
  миллиметров в отход, чем риск столкновения лазерной головы с зажимом).
- Рабочая зона для укладки заготовок: **5745 мм** (=6000-255).
- Формула итоговой обрези одной трубы (то, что попадает в отчёт и в
  файл кроя): `6000 − (сумма длин заготовок на трубе) − 30`. Тождественно
  равно `225 + неиспользованный остаток рабочей зоны`, где 225 = 215
  (зажим) + 10 (запас).
- Целевое поведение раскроя одной трубы (не жёсткое требование, а критерий
  качества, к которому стремимся): обрезь трубы должна попадать либо в
  диапазон "≤325 мм", либо в диапазон ">1250 мм" (точные формулировки
  диапазонов — см. раздел "Формат отчёта по раскрою"). Если ни то, ни
  другое не получается — оставить трубу как есть, не форсировать.
- **Не пытаться размещать заготовки в зоне зажима/технологических потерь.**
  Эта идея рассматривалась и была отклонена: риск неточной установки трубы
  оператором вручную (нет механических упоров) делает такой подход
  недопустимым.

## Источник данных

- Программа ищет в своей собственной папке (там, где лежит `.exe`; для
  `cargo run` — текущая папка запуска) файл
  `.xlsx`, имя которого начинается с "График производства" (без учёта
  регистра, с терпимостью к суффиксам вида " (1)", которые Windows
  добавляет при повторном скачивании).
  - Если файл не найден — понятная ошибка и остановка (без паники).
  - Если найдено несколько подходящих файлов — понятная ошибка со списком
    найденных файлов, просьба оставить один.
- Заголовки столбцов читаются из **первой строки листа**. Нужные столбцы
  ищутся **по названию заголовка** (обрезка пробелов, без учёта регистра),
  а не по номеру/букве колонки, так как порядок столбцов может отличаться
  у разных пользователей:
  - `Наименование` — из этого столбца берётся **только длина заготовки**
    в мм. Профиль/тип трубы из него не берём (см. раздел "Материал").
  - `Материал` — из этого столбца берётся **вся строка целиком** как
    ключ группировки. Ничего из неё не парсим отдельно (ни марку, ни
    профиль, ни отделку).
  - `Количество` — целое число копий данной строки.
  - `Обозначение` — идентификатор детали, для вывода в крой.
  - `Тип связи` — используется только для определения границы раздела
    (см. ниже).
  - Если хотя бы одного из обязательных столбцов (`Наименование`,
    `Материал`, `Количество`, `Обозначение`) нет в заголовках — явная
    ошибка с указанием, какого именно столбца не хватает, обработка не
    начинается.

## Определение обрабатываемого диапазона строк

- Диапазон "плавает" от файла к файлу, поэтому строки не хардкодятся.
- Начало раздела: первая строка, где первая колонка листа содержит текст
  `"Лазерная резка трубы"` (проверка по вхождению подстроки). Реальные
  данные начинаются со следующей строки.
- Конец раздела — берём **минимум** из двух сигналов (что наступит раньше):
  1. первая строка после начала, где колонка `Тип связи` пустая (стандартный
     признак строки-заголовка следующего раздела);
  2. первая строка после начала, где первая колонка содержит текст
     `"Столярный участок"`.
- Если раздел `"Лазерная резка трубы"` не найден вообще — явная ошибка,
  обработка не начинается.
- Если раздел найден, но между началом и концом нет ни одной пригодной
  строки — явная ошибка ("раздел найден, но пуст").
- **Найденный диапазон строк обязательно указывается в итоговом отчёте**
  (см. формат отчёта ниже) для визуальной проверки корректности.

## Извлечение длины из "Наименование"

- Ожидаемый формат: `Тр`/`тр`/`Труба`/`труба` (с пробелом после или слитно
  с размерами) + произвольные символы + число + `мм`.
- Разделитель дробной части в числе — запятая или точка, равнозначны.
- Всё, что идёт после числа с "мм" (уточнения вроде "разд", "отв 6мм",
  "левая" и т.п.) — не разбирается и не используется, полностью
  игнорируется при извлечении длины, НО сама исходная строка "Наименование"
  целиком используется дальше при выводе в файл кроя (см. ниже) —
  то есть для расчёта нужна только числовая длина, а для вывода нужен
  весь исходный текст.
- Ловушка, которую нужно учитывать: числа с "мм", которые НЕ являются
  длиной реза (например, `"Тр диаметр 51мм 842 мм"` — где 51мм это диаметр,
  а 842мм — длина реза; или `"отв 6мм"` — диаметр отверстия). Такие
  вложенные упоминания диаметра/отверстия должны быть исключены из поиска
  длины (маскированием по ключевым словам "диаметр", "отв"/"отверстие"
  перед основным числом с "мм"), чтобы не спутать их с искомой длиной.
- Если строка не начинается с одного из вариантов "Тр"/"тр"/"Труба"/"труба"
  (с учётом слитного написания с размерами) или число с "мм" вообще не
  найдено — строка не обрабатывается, попадает в список ошибок с указанием
  номера строки, исходного текста и причины ("не найдена длина" /
  "не распознан префикс").

## Обработка "Материал"

- Берём **всё содержимое ячейки как единую строку**, без попытки выделить
  из неё марку стали, профиль или отделку по отдельности. Ключ группировки
  = эта строка после нормализации:
  - привести к единому регистру для сравнения (само сравнение без учёта
    регистра), но для отображения (имя папки/файла) использовать текст
    **первого встреченного варианта** написания как канонический;
  - разделитель дробной части (запятая/точка) внутри строки материала
    считать эквивалентным для целей сравнения (но не менять его в
    отображаемом тексте).
- Разные по тексту строки материала (например, `"чернуха"` и `"ст3 х/к"`,
  или `"AISI 430"` и `"AISI 430 матовая"`) — это **разные материалы**,
  их **не нужно** пытаться объединять по смыслу. Каждая уникальная (после
  нормализации регистра/разделителя) строка материала — это отдельная
  группа/папка.
- **Исключения из раскроя** (не идут в упаковку, попадают в отчёт об
  ошибках с указанием причины, а также **обозначения и наименования**
  детали — не только номера строки, чтобы было проще ориентироваться):
  - материал пустой (ячейка не заполнена) — причина: "материал не указан";
  - материал содержит слово `"Лист"` (без учёта регистра) — причина:
    **"Материал указан как лист - проверьте ввод данных"** (точная
    формулировка);
  - количество указано, но не является числом — причина: "количество не
    распознано ('<исходное значение>')". Количество, равное 0 или вовсе
    не заполненное — не ошибка, просто пропускается молча (это означает
    "не заказано").

## Алгоритм упаковки (для одной группы "материал")

Заготовки внутри группы упаковываются в трубы рабочей длиной 5745 мм.
Не использовать полный перебор комбинаций (слишком медленно) — использовать
следующую комбинацию методов:

1. **Точная упаковка одной трубы (вариант C).** Для текущего остатка
   доступных заготовок находим **точно оптимальное** заполнение одной
   трубы (максимальная сумма длин, не превышающая 5745 мм), используя
   bounded knapsack по уникальным длинам (а не по каждой заготовке в
   отдельности — заготовок много, но уникальных длин внутри группы обычно
   немного, это и даёт скорость). Реализация — через битовые маски
   (собственный bitset на `Vec<u64>` длиной не менее 5746 бит; `u128` не
   хватает; допустим крейт `fixedbitset`) с бинарным разложением количества повторов
   каждой длины и последующей реконструкцией набора через снапшоты
   промежуточных состояний DP. Повторяем, пока остаются заготовки —
   получаем набор труб.
2. **Мультистарт внутри C.** Порядок обработки уникальных длин в DP влияет
   на то, какая именно комбинация выбирается при равнозначных вариантах
   заполнения — это создаёт пространство для улучшения без полного
   перебора. Для каждой группы запускаем несколько случайных запусков
   шага 1 (с перемешанным порядком длин), в рамках выделенного бюджета
   времени, и оставляем лучший результат по критерию: минимум труб с
   обрезью в диапазоне "от >326 мм до =1250 мм", при равенстве — меньше
   труб всего.
3. **Локальная чистка (вариант A).** После упаковки — один или несколько
   проходов переноса **одной** заготовки между трубами (не обмен, а именно
   перенос), чтобы перевести обрезь трубы либо в диапазон "≤325 мм",
   либо в диапазон ">1250 мм". Ограниченное число проходов (например, 3),
   не до полной сходимости любой ценой.
4. **Бюджет времени.** Общий бюджет на мультистарт по всему файлу — не
   более ~30-45 секунд суммарно (весь расчёт должен укладываться в
   диапазон 30 сек - 1 мин, включая парсинг файла). Реализовать как общий
   таймер с начала расчёта: пока есть запас времени — тратим его на
   мультистарт для очередной группы (пропорционально её размеру или просто
   поровну), как только общий лимит исчерпан — оставшиеся группы
   обрабатываются одним детерминированным проходом (шаг 1 без
   мультистарта) + шаг 3. Это гарантирует, что даже сильно выросший в
   будущем файл не приведёт к зависанию программы.
5. **Округление.** Для расчётов длины округляются до целых мм (точность
   более чем достаточная для лазерной резки трубы). В выводе показывать
   исходную длину как она была в файле (например "2179,2 мм"), округление
   влияет только на внутреннюю арифметику упаковки.

## Подбор файлов геометрии (iges)

Часть деталей — не просто отрезок трубы, а имеют дополнительную обработку
(отверстия под другие детали и т.п.), для которой на станке нужен файл
геометрии в формате `.iges`, извлечённый из 3D-модели детали.

### Поиск папки с iges-файлами

- Папка ищется рядом с программой **по содержимому, а не по фиксированному
  имени**: перебираются все подпапки рядом с программой, используется та,
  где есть хотя бы один файл `.iges` (поиск внутри неё — рекурсивный, на
  случай если файлы разложены по вложенным подпапкам).
- Если таких подпапок с `.iges`-файлами **не найдено ни одной** — это не
  фатальная ошибка: функция подбора геометрии просто отключается на этот
  запуск, о чём выводится явное предупреждение в консоль. Расчёт кроя
  (текстовые файлы) при этом всё равно формируется как обычно.
- Если подпапок с `.iges`-файлами найдено **несколько** — явная ошибка
  окружения (аналогично нескольким подходящим `.xlsx`), с перечислением
  найденных папок, обработка не начинается.

### Правило сопоставления детали и файла

- Ожидаемое имя файла геометрии: `<Обозначение>_<Наименование>.iges`, где
  вокруг символа `_` возможны пробелы (`Обозначение _Наименование.iges`,
  `Обозначение_ Наименование.iges`, `Обозначение _ Наименование.iges` — все
  варианты равнозначны).
- Сопоставление ведётся по нормализованному ключу: у имени файла (без
  расширения) убираются пробелы вплотную к `_`, повторяющиеся пробелы
  схлопываются в один, обрезаются пробелы по краям; такая же нормализация
  применяется к строке `<Обозначение>_<Наименование>`, собранной из данных
  того же кроя. Совпадение — точное, после нормализации.
- Все `.iges`-файлы индексируются **один раз** в начале работы (словарь
  "нормализованный ключ → путь к файлу"), дальше по каждой детали — просто
  поиск в этом словаре, без повторного сканирования диска.
- Если одна и та же деталь (по обозначению+наименованию) встречается в
  одном крое несколько раз (разные строки/количество) — в папку кроя
  копируется **одна** копия найденного файла геометрии, дублирование не
  нужно (это одна и та же геометрия).
- Если для нормализованного ключа находится **больше одного** файла
  (дубликаты в самой папке с геометрией) — это тоже фиксируется как
  ошибка поиска (см. ниже), с перечислением всех найденных путей;
  копирование в этом случае не выполняется, чтобы не выбирать наугад.

### Логирование ненайденных файлов

- **Любое** отсутствие соответствия — повод для записи в файл ошибок
  поиска геометрии данного кроя (`Ошибки поиска геометрии.txt`, внутри
  папки этого конкретного кроя), независимо от того, простая это деталь
  (нужен ли ей вообще iges) или нет — окончательное решение, было ли это
  ожидаемо, остаётся за оператором/технологом.
- Формат строки в файле ошибок поиска:
  `<Обозначение>  <Наименование> — файл геометрии не найден`
  (для случая дубликатов — `<Обозначение>  <Наименование> — найдено
  несколько файлов геометрии: <путь1>, <путь2>, ...`).
- Этот файл создаётся в папке кроя, **только если** для этого кроя есть
  хотя бы одна такая запись — в норме (всё нашлось) файла не будет.

## Структура результата на диске

Рядом с программой создаётся одна папка результата (например
`Раскрой_<дата>`), внутри неё:

- `Отчёт об ошибках на <дата>.txt` — шапка с источником/константами + список
  ошибок и исключений (см. формат ниже);
- `Отчёт по раскрою трубы на <дата>.txt` — та же шапка + статистика по
  диапазонам обрези, отдельным блоком на каждый материал (см. формат ниже);
- по одной подпапке на каждый уникальный материал, имя папки = сама строка
  материала (канонический вариант написания), очищенная от символов,
  недопустимых в именах файлов Windows (`\ / : * ? " < > |` — заменить на
  дефис или пробел);
- внутри каждой папки материала — **по одной подпапке на каждую трубу**,
  имя подпапки = `Крой N <материал>` (без расширения). Внутри этой
  подпапки:
  - текстовый файл `Крой N <материал>.txt` с тем же содержимым, что и
    раньше (список заготовок + строка обрези);
  - скопированные `.iges`-файлы геометрии для тех деталей этого кроя, для
    которых нашлось соответствие (см. раздел "Подбор файлов геометрии
    (iges)" ниже);
  - `Ошибки поиска геометрии.txt` — только если хотя бы для одной детали
    файл геометрии не нашёлся (см. ниже). В норме этого файла быть не
    должно.

### Формат файла одной трубы (`Крой N <материал>.txt`)

```
Крой N <материал>

1. 2179,2 мм — RST-ШДХ-0.65х0.35х2.2-01.00.003  Труба 40x40x1 2179,2 мм  x2
2. 1390 мм — ВС3С-1.5х0.5х0.85-01.00.004  Труба 40x40x1 1390 мм
-> Обрезь ~251,6 мм
```

Пояснения:
- **первая строка файла — то же имя, что и у самого файла/папки кроя**
  (без расширения `.txt`), затем пустая строка-разделитель;
- порядок деталей на трубе значения не имеет (зажатый участок не
  используется, "довыпиливание хвоста" отменено ранее), поэтому
  **одинаковые детали (совпадают Обозначение, Наименование и длина)
  объединяются в одну строку** с указанием количества через `xN` в конце
  строки; если деталь в этом крое встречается один раз — суффикс `xN` не
  пишется (чтобы не засорять типичный случай);
- нумерация строк (`1.`, `2.`, ...) — по количеству **уникальных** деталей
  на трубе, не по количеству физических отрезков;
- каждая строка заготовки: `<номер по порядку>. <длина> мм — <Обозначение>
  <пробел> <Наименование целиком>` (+ `  xN`, если количество больше 1);
- длина в строке — как в исходном файле (не округлённая);
- последняя строка — только величина итоговой обрези (калибровочные 30 мм
  в неё не входят — см. "Физическая модель раскроя"), **без каких-либо
  пояснений** (никаких словесных ярлыков, только сама величина — этого в
  файле кроя быть не должно, такие пояснения только в общем отчёте).

### Общая шапка (используется в начале ОБОИХ файлов отчёта)

```
РАСКРОЙ ТРУБЫ <дата>
Источник: <имя файла>.xlsx, раздел 'Лазерная резка трубы' (строки X-Y)
Исходная труба: 6000 мм | Калибровка (отдельно, отрезается первой): 30 мм |
Технологические потери всего: 255 мм (30 калибровка + 215 зажим + 10 запас) |
Рабочая зона: 5745 мм
Время расчёта: N.NN сек
========================================================================
```

### Формат `Отчёт по раскрою трубы на <дата>.txt`

После общей шапки — блок на каждый материал:

```
ИТОГО труб <материал 1>: N
  - Обрезь (включая технологические потери 255мм) <= 325 мм: N труб
  - Обрезь (включая технологические потери 255мм) от >326 мм до =1250 мм: N труб
  - Обрезь (включая технологические потери 255мм) > 1250 мм: N труб

ИТОГО труб <материал 2>: N
  ...

(повторяется для каждого материала)
```

### Формат `Отчёт об ошибках на <дата>.txt`

После общей шапки:

```
ОШИБКИ И ИСКЛЮЧЕНИЯ ИЗ РАСКРОЯ (N строк, требуют проверки):
  стр.NNNN: <Обозначение>  <Наименование целиком> — <причина>
  ...
```

Причины в списке ошибок формулируются явно: `"не найдена длина"`,
`"не распознан префикс трубы"`, `"материал не указан"`,
`"Материал указан как лист - проверьте ввод данных"`,
`"количество не распознано ('...')"`,
`"длина заготовки (N мм) превышает рабочую зону трубы (5745 мм)"`.

## Проверки и обработка ошибок окружения

Каждая из следующих ситуаций должна давать понятное сообщение на русском
языке и корректную остановку программы (без паники и трассировки), с паузой
перед закрытием окна консоли:

- исходный `.xlsx` не найден рядом с программой;
- найдено больше одного подходящего `.xlsx`;
- не удалось открыть файл (повреждён/не является Excel);
- не хватает одного или нескольких обязательных столбцов;
- раздел `"Лазерная резка трубы"` не найден;
- раздел найден, но в нём нет ни одной обрабатываемой строки.

## Проверка целостности (встроенная в программу)

После формирования раскроя для каждой группы материала — сверить, что
множество заготовок "на входе" (по совокупности длина+обозначение+номер
строки исходного файла) **точно совпадает** с множеством заготовок,
распределённых по трубам на выходе (ничего не потеряно, ничего не
задвоено). При расхождении — явное сообщение об ошибке в консоли,
отчёт не считать надёжным.

## Что специально НЕ делать

- Не пытаться размещать заготовки в зоне технологических потерь (255 мм,
  включая калибровку).
- Не пытаться "по смыслу" объединять разные строки материала (например,
  "чернуха" и "ст3 х/к") — это разные материалы по определению базы.
- Не делать полный перебор комбинаций упаковки.
- Не выводить в файлы кроя никаких пояснений/комментариев кроме итоговой
  величины обрези.

# Тестовые сценарии

## Автоматизация тестов (Rust)

- Тесты ниже по возможности оформляются как автотесты `cargo test`:
  юнит-тесты для `parse.rs` и `pack.rs` (в модулях, `#[cfg(test)]`),
  интеграционные — в `tests/`, с генерацией временных `.xlsx` во
  временной папке (например, крейт `tempfile`).
- Перед коммитом должны проходить `cargo fmt --check`,
  `cargo clippy -- -D warnings` и `cargo test` (то же самое выполняет CI).
- **Сверка с Python-оригиналом.** Тесты 1, 16 и 17 дополнительно
  выполнить на одном и том же исходном файле обеими версиями: тексты
  отчётов, нормализация материалов и состав труб (число труб, суммы по
  диапазонам обрези) должны совпадать; допускается различие только в
  конкретной раскладке из-за случайного мультистарта.

## Функциональные тесты на синтетических данных

1. **Базовый happy path.** Собрать небольшой синтетический Excel (5-10
   строк, 2-3 материала, реалистичные длины) с корректной структурой.
   Ожидается: создана папка результата, внутри — отчёт и подпапки по
   числу уникальных материалов, файлы `Крой N ...` с правильным числом
   труб и корректным списком заготовок в каждой.
2. **Слияние по регистру/разделителю.** В тестовых данных сделать две
   строки материала: `"Ст3 х/к"` и `"ст3 х/к"` — должны попасть в ОДНУ
   папку. Отдельно — `"труба d30x1,5"` и `"труба d30x1.5"` (в тексте
   материала) — тоже должны считаться одним материалом.
3. **НЕ слияние похожих, но разных материалов.** `"чернуха"` и
   `"ст3 х/к"` — должны остаться в РАЗНЫХ папках, даже если физически
   похожи.
4. **Исключение "Лист".** Строка с материалом, содержащим слово "Лист"
   (в любом регистре, в любом месте строки) — не должна попасть ни в один
   крой, должна появиться в списке ошибок с правильной причиной.
5. **Исключение пустого материала.** Строка с пустой ячейкой материала —
   аналогично, исключена и залогирована.
6. **Некорректное "Наименование".** Набор строк без длины, без нужного
   префикса, с "мусорными" текстами вроде "Неудаленная деталь" — все
   должны попасть в список ошибок, не должны прерывать обработку
   остальных строк.
7. **Ловушка "диаметр"/"отверстие".** Строка вида `"Тр диаметр 51мм 842
   мм"` — длина должна распознаться как 842, а не 51. Строка вида
   `"Тр 40х20х2 730мм отв 6 мм"` — длина 730, а не 6.

## Тесты устойчивости к структуре файла

8. **Другой порядок столбцов.** Тот же набор данных, но столбцы
   переставлены местами (например, "Материал" левее "Наименование") —
   результат должен быть идентичен тесту 1, так как поиск идёт по
   заголовкам.
9. **Другой диапазон строк раздела.** Тот же раздел "Лазерная резка
   трубы", но начинается не с 10-й, а, скажем, с 500-й строки листа, с
   произвольным количеством строк до и после — раздел должен быть найден
   корректно, границы указаны верно в отчёте.
10. **Конец раздела без "Столярный участок".** Раздел заканчивается не
    словами "Столярный участок", а любым другим текстом в следующей
    строке с пустой колонкой "Тип связи" — конец должен определиться
    верно по этому альтернативному сигналу.

## Тесты на ошибки окружения

11. Запуск в папке без `.xlsx` файла — понятная ошибка, без паники.
12. Два `.xlsx` файла, оба подходящие по имени — понятная ошибка со
    списком файлов.
13. Файл есть, но отсутствует колонка "Материал" — понятная ошибка с
    точным указанием, какой колонки не хватает.
14. Файл есть, но раздела "Лазерная резка трубы" в нём нет — понятная
    ошибка.
15. Раздел есть, но пустой (сразу за маркером начала следует маркер
    конца) — понятная ошибка "раздел пуст".

## Тесты на реальных данных

16. **Прогон на полном файле "График производства.xlsx"** (актуальная
    версия). Проверить: время расчёта укладывается в 30-60 сек; ни одна
    заготовка не потеряна/не задвоена (автоматическая проверка
    целостности встроена в саму программу, тест лишь подтверждает, что она
    прошла); суммы по диапазонам обрези в отчёте совпадают с суммой труб
    по всем материалам; количество файлов `Крой N ...` в каждой папке
    совпадает с числом труб, указанным в отчёте для этого материала.
17. **Повторный запуск с теми же данными.** Два последовательных запуска
    на одном и том же файле должны давать **валидный** результат в обоих
    случаях (проверка целостности проходит), даже если из-за мультистарта
    конкретная раскладка чуть отличается между запусками — это ожидаемо
    и не является браком, но само число труб не должно "скакать"
    значительно от запуска к запуску.

## Нагрузочный/граничный тест

18. **Заготовка длиннее рабочей зоны.** Синтетическая строка с длиной,
    например, 5800 мм (больше 5745) — не должна попасть в обычный крой
    (её физически нельзя вырезать из 6000-мм трубы с учётом технологических
    потерь), должна быть отдельно отмечена в отчёте как невозможная к
    изготовлению, а не молча пропущена или не вызвать ошибку/зависание
    упаковщика.
19. **Очень большое количество одинаковых длин** (например, 500 заготовок
    одной длины 1000 мм в одной группе) — упаковка должна отработать
    быстро (это именно тот случай, для которого выбран bounded knapsack
    по уникальным длинам, а не перебор по каждой заготовке).

## Тесты на подбор файлов геометрии (iges)

20. **Точное совпадение.** Синтетический `.iges`-файл с именем ровно
    `<Обозначение>_<Наименование>.iges` — должен быть найден и скопирован
    в папку соответствующего кроя.
21. **Совпадение с пробелами вокруг `_`.** Тот же тест, но имя файла —
    `<Обозначение> _ <Наименование>.iges` (и варианты с пробелом только с
    одной стороны) — должно матчиться так же успешно, как и тест 20.
22. **Файл не найден.** Деталь без соответствующего `.iges` в папке —
    в папке её кроя должен появиться `Ошибки поиска геометрии.txt` с
    правильной записью; сам крой при этом должен сформироваться нормально
    (отсутствие геометрии не блокирует расчёт раскроя).
23. **Все детали кроя нашли геометрию.** Файла `Ошибки поиска
    геометрии.txt` в папке этого кроя быть не должно вообще (ни пустого,
    ни с записями).
24. **Повтор детали в одном крое.** Деталь встречается в кроe дважды
    (количество 2 на одной строке или две одинаковые строки) — в папку
    кроя должна попасть **одна** копия `.iges`, не две.
25. **Дубликаты в самой папке геометрии.** Два разных `.iges`-файла в
    исходной папке дают одинаковый нормализованный ключ — должна
    появиться запись в файле ошибок поиска с перечислением обоих путей,
    копирование для этой детали не выполняется.
26. **Папка с iges не найдена вовсе.** Рядом с программой нет ни одной
    подпапки с `.iges`-файлами — программа не падает, выводит понятное
    предупреждение, текстовые файлы кроя формируются как обычно, просто
    без геометрии и без файлов ошибок поиска.
27. **Несколько подпапок с iges одновременно.** Рядом с программой две
    разные подпапки, в каждой есть `.iges`-файлы — явная ошибка окружения
    со списком найденных папок, обработка не начинается (аналогично
    нескольким `.xlsx`-кандидатам).
28. **Реальные данные.** Прогон на реальной папке с `.iges`-файлами (когда
    появится) — оценить, у какой доли деталей в принципе находится
    геометрия, и есть ли неожиданно большие списки в `Ошибки поиска
    геометрии.txt` (это будет сигналом либо о проблеме с сопоставлением,
    либо о реальных пробелах в комплекте файлов геометрии).
